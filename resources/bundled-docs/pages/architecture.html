System Boundary

vi-history-suite is a VS Code desktop extension for expert review of LabVIEW VI history in Git repositories.

The architecture is intentionally local-first and bounded:

  • the user works inside VS Code
  • Git history and tracked-file state come from local Git plus the built-in vscode.git extension
  • VI review happens through governed history, comparison-report, dashboard, and decision-record surfaces
  • documentation-package work and future wiki seeding use a separate docs-authoring workbench instead of the runtime proof lanes

Main Containers

The governed architecture overview currently distinguishes these major containers:

  • extension manifest for commands, menus, and settings
  • extension runtime for indexing, trust gating, and command execution
  • Git adapter for tracked-file and history queries
  • review UI for history presentation and review actions
  • report subsystem for planning, runtime/tool selection, report execution, and retained dashboard preparation
  • harness smoke runner for canonical proof lanes
  • governance pack for requirements, ADRs, RTM, and tests
  • documentation-package workbench for requirements and release-doc iteration
  • cross-repo navigation surface for jumping between the product repo, wiki repo, and companion assurance-skill repo

Review Architecture

The core review flow is split deliberately:

  • history-panel review is the bounded chronology surface
  • pairwise NI comparison reports are retained evidence for adjacent revisions
  • the multi-report dashboard is the concentration surface for one VI across at least three commits
  • human decision records stay separate from machine-generated evidence

This separation matters because the product is meant to reduce reviewer wear without pretending to replace human judgment.

Runtime And Isolation

Comparison-report generation is governed separately from the basic history experience.

Key architectural decisions in the current baseline:

  • Windows 64-bit isolated container execution is the preferred extension-user path when available
  • host-native execution remains relevant primarily for bounded Windows x86 cases
  • Linux can serve as an explicit extension-host proof lane for faster local iteration
  • retained packets and dashboards are rendered locally in the extension so already-built HTML evidence is usable without depending on external navigation behavior

Documentation And Control Plane

The architecture now explicitly includes design-governance surfaces, not just runtime components.

Important control-plane decisions include:

  • docs-authoring workbench image for governed documentation-package iteration
  • authority-first wiki seeding from requirements, ADRs, RTM, current-state, and ship-control docs
  • governed wiki workbench CLI and retained publication-prep receipts for derived wiki widening
  • cross-repo navigation control plane tying together:
    • vi-history-suite
    • vi-history-suite.wiki
    • repo-standards-review

That means future documentation and wiki work is expected to start from the repo docs stack, not from source spelunking.

The current wiki lane is intentionally evidence-bearing:

  • the main repo remains the authority of record
  • the wiki remains a derived reader surface
  • publication state stays tied to the wiki publication ledger
  • local and Docker-first workbench commands prepare pages before publication
  • stale retained page directories are recovered into explicit writable staging-runs/ or publication-prep-runs/ paths instead of silently bypassing the governed workbench

Current Tradeoffs

The architecture currently accepts these important tradeoffs:

  • Git on PATH remains a runtime dependency
  • dashboard ETA is characterized from retained evidence but not yet treated as a calibrated release gate
  • documentation-package iteration is intentionally separated from NI runtime proof
  • the product still tracks a release blocker for the remaining progress, cancellation, and trust-aware UX layer
