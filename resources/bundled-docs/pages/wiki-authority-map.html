Wiki Authority Map

This page is derived from governed repository documentation, not from source code or prior chat state. The current authority surfaces for this page are:

  • docs/product/wiki-authority-map.md
  • docs/documentation-workbench.md
  • docs/product/wiki-seed-plan.md
  • docs/product/current-state.md

Purpose

The wiki authority map defines how wiki content for vi-history-suite is supposed to be created and refreshed.

Its job is to keep the wiki derived from governed documentation instead of from source-code spelunking, shell output, or prior chat memory.

Authority Order

When wiki pages are created or refreshed, the current authority order begins with the strongest product-control surfaces:

  1. SHIP-0001
  2. release-readiness matrix
  3. blocker ledger
  4. development queue
  5. current state
  6. SRS
  7. RTM
  8. test plan
  9. documentation coherence ledger
  10. wiki seed plan
  11. wiki publication ledger
  12. wiki publication ledger JSON
  13. architecture overview
  14. active ADRs
  15. README
  16. research alignment
  17. research implementation index

If two sources disagree, the higher source wins until the lower one is corrected.

Excluded Inputs

The wiki authority model explicitly excludes these as primary truth sources:

  • src/
  • tests/
  • transient shell output
  • prior chat messages

Those surfaces can help locate evidence, but the claim still has to be verified back against the governed docs package.

Readiness Gate

Before widening or refreshing a wiki page, these things should already be true:

  • the latest retained design gate is passing
  • the current-state and ship-control surfaces agree
  • requirements, tests, architecture, and control-plane docs do not have an unresolved contradiction
  • the documentation workbench is current enough for the wiki change
  • the wiki workbench doctor reports no error-level topology or ledger issue
  • the publication ledger is updated when a page is truly published
  • the bundled docs are refreshed when the published wiki set changes

This is what keeps the wiki from becoming a second uncontrolled authority.

Incremental Workflow

The current governed flow is:

  1. read the authority order from top to bottom
  2. use the wiki workbench to resolve the published set and next page
  3. draft only the bounded page currently being widened
  4. prefer requirement and ADR wording over implementation inference
  5. cite governed repo-relative docs for substantive claims
  6. promote any source-only fact into the docs package first
  7. retain a page-authority bundle and publication-prep receipt before publication
  8. refresh the packaged bundled docs after the published wiki set changes

High-Value Inputs

The current high-value wiki inputs are:

  • install and release surfaces
  • user workflow surfaces
  • architecture and ADRs
  • documentation workbench guidance
  • program repo jump and cross-repo orientation
  • documentation coherence ledger
  • wiki seed plan and publication ledger
  • proof and verification surfaces such as RTM and test plan

Why It Matters

The wiki authority map is one of the main controls that keeps the wiki useful instead of merely convenient.

It makes three boundaries explicit:

  • the main repo docs are the authority of record
  • the wiki is a derived reader surface
  • publication is only one step in a broader governed documentation system
