Comparison Report Contract

vi-history-suite treats a VI comparison report as governed retained evidence, not as a transient shell output.

The retained comparison-report flow currently covers:

  • revision-pair preflight against content-detected VI blobs
  • runtime/tool selection
  • retained packet and metadata persistence under workspace-scoped storage
  • reliable governed NI report generation on the preferred Windows 64-bit isolated container path
  • rendering of retained comparison evidence inside the extension

The comparison-report surface is intended to remain factual even when NI report generation is blocked, cancelled, or only partially complete.

Observed NI Metadata

The dashboard contract is derived from actual observed NI report metadata, not from invented reviewer fields.

The currently inventoried NI comparison report surfaces include:

  • report title
  • generation time
  • compared VI paths
  • overview section captions
  • overview image counts per section
  • included attributes
  • detailed-information headings
  • detailed-information items

The canonical observed inventory is retained in:

Runtime Doctor

The comparison-report subsystem also retains a compact runtime-doctor summary so users do not need raw logs first.

That retained runtime-doctor surface includes:

  • chosen provider
  • chosen engine
  • platform
  • preferred bitness
  • selected runtime tools
  • blocked or failure reason when present
  • one bounded next action

Retained Pair Review

At the history-panel level, pair review is intentionally stateful.

  • Generate compare creates retained pair evidence when it does not exist yet
  • Refresh compare reruns pair evidence generation for an already retained pair
  • Open compare opens retained pair evidence when it already exists
  • Diff prev uses retained comparison evidence for governed VI review instead of falling back to VS Code’s unsupported text diff on binary VI content

If retained pair evidence is missing, the extension fails closed and directs the reviewer to generate that evidence first.

Dashboard Review

The multi-report dashboard is the concentration surface for one VI across at least three commits.

The dashboard currently concentrates retained NI metadata across the commit window, including:

  • chronology-first pair metadata
  • whole-window overview-caption concentration
  • whole-window included-attribute concentration
  • whole-window detailed-information heading concentration
  • whole-window compared-path concentration
  • whole-window detail-item concentration
  • overview image counts and retained overview image assets

The dashboard is intended to reduce the wear of opening every pairwise report while keeping the underlying pair evidence available when the reviewer decides to drill down.

Progress, Cancellation, And Trust

Report and dashboard work are long-running enough that the extension treats them as governed progress surfaces.

Current behavior includes:

  • bounded progress during report and dashboard refresh
  • trust-aware refusal in untrusted workspaces
  • retained partial evidence when cancellation happens after artifacts are built
  • cancellation honored before comparison-report and dashboard panel open

That means the extension is designed to preserve already-built evidence instead of opening a panel after cancellation or silently discarding retained artifacts.

Proof Surfaces

The repo currently retains dedicated proof lanes for both pairwise reports and dashboard concentration:

  • canonical comparison-report smoke
  • canonical dashboard smoke
  • real extension-host dashboard proof

Those proof surfaces exist so future sessions can verify the review flow from retained evidence instead of from chat memory.

Exact-Pair Diagnosis

PROGRAM-0003 now depends on exact-pair diagnosis reruns for the first invalid benchmark boundaries.

Those reruns are governed, not ad hoc. The canonical rules now include:

  • --selected-hash and --base-hash must be supplied together
  • both hashes must be full 40-character git hashes
  • explicit runtime override paths require matching --platform and --engine
  • Windows --prefer-bitness must not contradict explicit Program Files / Program Files (x86) runtime paths
  • explicit Windows runtime override bundles must not mix x86 and x64 paths even when --prefer-bitness is omitted
  • wrong engine/path combinations fail closed before the harness runs

That admission control is no longer exact-pair-only:

  • dashboard-smoke, decision-record, exact-pair smoke, and the Windows/Linux benchmark CLIs now share the same canonical runtime-override validation layer before retained evidence is generated

The current operator-facing authority for that contract is:

  • docs/product/canonical-exact-pair-diagnosis.md
  • docs/architecture/adr/ADR-0022-canonical-experiment-admission-control.md

That canonical contract now also includes Windows host hygiene:

  • explicit Windows runtime override paths must exist before a targeted rerun starts on the canonical host
  • canonical Windows host-native reruns fail closed when stale LabVIEW.exe, LabVIEWCLI.exe, or LVCompare.exe sessions are already open
  • canonical Windows host-native reruns fail closed when the selected LabVIEW.ini-derived VI Server TCP port already has a listener before launch
  • on the current canonical machine, only the x86 LabVIEWCLI.exe path exists, so host-native x64 labview-cli exact-pair reruns are non-canonical unless a real x64 CLI install exists

The packet admission rule for exact-pair benchmark-image proof is now fail-closed too:

  • the comparable-prefix packet searches the live and archived .prev-* exact-pair smoke receipts under each proof root
  • it admits only the latest receipt that still proves the governed Windows benchmark-image surface through retained container-context markers such as C:\workspace\.cache clone or artifact paths and, when available, C:\Users\ContainerAdministrator\... diagnostic-log sources
  • those retained exact-pair comparison-report-smoke receipts now also persist executionSurfaceContext plus executionSurfaceMarkers when those retained markers prove that governed Windows benchmark-image surface
  • if a newer rerun under the same proof root no longer proves that surface, the packet records it as a rejected contaminated rerun instead of promoting it to benchmark-image truth

Ambient environment changes such as LV_RTE_HEADLESS=1 can still support bounded characterization work, but they do not replace the canonical admission contract.
