Queued Execution Flexibility State

The repo now also carries a separate user-facing execution-policy lane whose four bounded implementation slices have already landed.

Current implemented truth:

  • the installed extension now exposes viHistorySuite.executionMode
  • auto, host-only, and docker-only are explicit runtime-selector truths
  • host-only and docker-only now fail closed instead of silently substituting the other provider class
  • on Windows, auto now stays host-native on a clean validated host instead of selecting Docker just because a governed image exists
  • the selector now derives the selected LabVIEW.ini, governed VI Server TCP port, and observed host-runtime conflict facts before final Windows provider choice
  • Windows Docker-capability truth is now explicit too: the selector validates Docker CLI availability, daemon reachability, active container mode, and governed image presence before the Windows provider is selected or rejected
  • when Windows container execution is selected and the governed image is missing, comparison-report generation now surfaces governed image-pull progress before packet persistence and runtime launch
  • contaminated Windows host-runtime surfaces now route to Docker when the governed provider is available and hard-stop when Docker is required but not available
  • retained runtime-doctor and packet surfaces now carry acquisition state and acquisition-failure hard stops explicitly
  • the history panel now also retains the latest compare-runtime summary with selected provider, rejected-provider reasons, execution mode, acquisition state, and next action
  • blocked or failed compare actions now also emit one concise mode-aware warning using that same retained runtime truth

The remaining queued control plane says:

  • provider choice should start from one canonical effective execution request, not from scattered settings or ambient runtime guesses
  • compatible host LabVIEW 2026 Q1 x86 or x64 execution remains valid when the selected mode permits host-native launch and the host surface is clean
  • auto should stay host-native on a clean host instead of acquiring Docker by habit
  • if an already-open host LabVIEW 2026 session or governed VI Server collision would contaminate host execution, auto requires Docker instead of silently continuing on the host
  • host conflict truth is tied to the selected LabVIEW.ini and derived VI Server TCP port
  • if Docker is required and unavailable, or not Windows-container-capable on a Windows host, the product contract is a hard stop telling the user to close LabVIEW or install, enable, or switch Docker
  • when Docker is evaluated on Windows, the retained runtime-doctor and packet surfaces now expose those Docker capability facts instead of collapsing them into one image-availability guess
  • the current comparison-report path now shows visible pull progress when Windows container execution still requires the governed Windows image
  • fuller front-facing provider/acquisition transparency beyond the current progress, compare-warning, history-panel, runtime-doctor, and retained- packet surfaces remains the open PROGRAM-0005 remainder
  • the current open debt item for that ambiguity is retained in the authority debt ledger rather than left implicit
