Purpose

This page explains how vi-history-suite keeps requirements and verification governed instead of informal.

The current model is three-part:

  • the SRS states what the product shall do
  • the RTM ties requirements to proof surfaces
  • the test plan states how those proofs are exercised and reviewed

The requirements package now also retains an explicit execution-mode contract for installed-extension runtime choice, so host-versus-Docker behavior does not remain only an implementation detail.

SRS

The Software Requirements Specification is the main normative requirement surface.

It covers:

  • command and review-surface behavior
  • runtime-provider and benchmark behavior
  • the execution-mode contract for auto, host-only, and docker-only, including the already-landed execution-mode, host-fact, Docker-capability, Windows acquisition-progress slice, and history-panel latest compare-runtime summary slice plus the remaining front-facing transparency work
  • documentation-package and wiki-workbench behavior
  • bounded repo-family support
  • release, setup, and control-plane rules

Requirements use stable identifiers such as VHS-REQ-001 and continue through the current governed product surface.

RTM

The requirements traceability matrix is the machine-readable bridge from requirements to proof.

For each requirement it records:

  • the requirement id
  • priority and source
  • mapped test ids
  • test artifacts
  • code or doc references
  • implementation status

This is what lets the docs gate fail on real drift instead of on opinion.

Test Plan

The test plan defines the verification inventory across:

  • unit tests
  • integration tests
  • smoke lanes
  • documentation reviews

It is not only a list of tests. It is also the governed surface that explains what kinds of evidence are expected for each part of the product.

Current Truth

The current repo already enforces requirements coherence through the docs gate.

That means:

  • SRS and RTM must align
  • RTM and test-plan ids must align
  • documentation-package control surfaces must stay coherent

The product now also carries wiki and packaged-doc requirements in the same governed requirements system rather than treating documentation as informal.

That same system now governs the partially implemented execution-mode contract too, including:

  • the installed setting surface for auto, host-only, and docker-only
  • the no-silent-fallback rule between host-only, docker-only, and auto
  • when Windows auto must stay host-native because the selected host surface is clean
  • when the selected LabVIEW.ini and derived VI Server TCP port define the current host conflict boundary
  • when a contaminated Windows host surface now routes to Docker or hard-stops instead of silently continuing on the host
  • when the extension now validates one canonical effective execution request before provider selection or Docker acquisition starts
  • when Docker becomes a hard requirement because an open host LabVIEW session would contaminate host execution
  • when Windows Docker evaluation must distinguish Docker CLI availability, daemon reachability, active container mode, and governed image presence before the Windows provider is selected or rejected
  • when the extension must tell the user to close LabVIEW or install Docker
  • when Windows must tell the user to start Docker or switch to Windows containers before a governed Windows image can run
  • when Windows now surfaces visible progress while pulling the governed Windows image and retains acquisition state in the comparison-report packet and runtime-doctor surfaces

Why It Matters

This is one of the main differences between a useful engineering wiki and a shallow summary surface.

The wiki does not replace the SRS, RTM, or test plan. It represents them for readers, while the authority remains in the main repo.
