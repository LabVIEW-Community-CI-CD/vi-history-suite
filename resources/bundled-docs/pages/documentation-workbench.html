Purpose

The documentation workbench is the governed authoring surface for the documentation package of vi-history-suite.

It exists so documentation work can stay disciplined while still being fast:

  • requirements, RTM, and test-plan edits
  • ADR and architecture updates
  • release-readiness and control-plane documentation
  • authority-first wiki staging and publication prep
  • bundled user-document refresh work

It is not the NI comparison-report proof lane and it is not the extension-user install surface.

Operating Model

The workbench keeps a strict boundary between authority and publication:

  • the main vi-history-suite repo is the authority of record
  • vi-history-suite.wiki is a derived reader surface
  • wiki work should start from governed docs, not from source spelunking or prior chat state
  • publication state remains tracked in the main repo through the wiki publication ledger and retained workbench receipts
  • the wiki is only considered finished when the authority repo's zero-gap wiki coverage matrix says every in-scope standards surface is represented on published wiki pages

That means a wiki page is prepared from governed inputs first and only treated as published after the wiki repo is actually updated.

Workbench Surfaces

The workbench currently supports both local and Docker-first operation.

Local commands:

  • npm run wiki:workbench:doctor
  • npm run wiki:workbench:plan
  • npm run wiki:workbench:prepare
  • npm run wiki:workbench:sync-bundled-docs

Docker-first equivalents:

  • npm run docs:workbench:wiki:doctor
  • npm run docs:workbench:wiki:plan
  • npm run docs:workbench:wiki:prepare
  • npm run docs:workbench:wiki:sync-bundled-docs

The workbench resolves the governed repo constellation instead of assuming ad hoc shell paths:

  • vi-history-suite
  • vi-history-suite.wiki
  • the wiki publication ledger
  • the local repo-jump map used for cross-repo navigation

Published Image And GitLab Lane

The workbench also has a published-image lane for authoritative documentation iteration.

GitLab publishes the docs-authoring image as:

  • registry.gitlab.com/svelderrainruiz/vi-history-suite/docs-authoring:main
  • registry.gitlab.com/svelderrainruiz/vi-history-suite/docs-authoring:sha-<commit>
  • registry.gitlab.com/svelderrainruiz/vi-history-suite/docs-authoring:vX.Y.Z on governed tags

That matters because the wiki lane is supposed to be reproducible. Local Docker iteration is useful, but the stronger automation surface is the repo-published image plus the retained workbench evidence from the authoritative pipeline.

Retained Evidence

The workbench is designed to retain preparation state, not just produce a page draft.

Important retained outputs include:

  • .cache/wiki-workbench/latest-workbench.json
  • .cache/wiki-workbench/staging/<page-id>/
  • .cache/wiki-workbench/publication-prep/<page-id>/publication-prep.json
  • docs-workbench-evidence/docs-workbench-manifest.json from the published docs-authoring image lane
  • wiki-workbench-evidence/ when the GitLab wiki-preparation lane is widened further

Those retained files matter because they let future sessions see:

  • which page was targeted
  • which authority docs were used
  • what the staged wiki draft looked like
  • whether publication prep actually completed

If a stale retained page directory is locally unwritable, the workbench now rotates to a writable recovery path instead of failing solely on old cache ownership:

  • .cache/wiki-workbench/staging-runs/<page-id>-<timestamp>/
  • .cache/wiki-workbench/publication-prep-runs/<page-id>-<timestamp>/

The stage or publication-prep receipt records the actual retained path, so the recovery is still explicit and reviewable.

Governed Flow

The intended sequence is:

  1. run doctor to validate topology, ledger state, and authority readiness
  2. run plan to resolve the current page set and any remaining next target page when the coverage matrix is not yet zero-gap
  3. run prepare to retain the page-authority bundle, draft page, and publication-prep receipt
  4. run sync-bundled-docs only when the staged wiki state is ready to drive bundled user-document updates

The workbench is fail-closed. If the sibling wiki repo, control files, ledger targets, or authority docs are wrong, it stops instead of producing weak wiki input.

This is deliberate. The wiki lane is meant to be a governed derived-publication surface, not a convenient prose scratchpad.

Publication State

The wiki publication ledger remains the main source for actual publication state.

That ledger records:

  • which pages are published
  • which wiki commit carried them
  • their publication date
  • the primary authority docs for each page

The completion contract is stricter than the publication ledger alone. The authority repo now also keeps a wiki coverage matrix that lists every in-scope requirements-and-standards source plus every ADR file and only treats the wiki as finished when every row is complete and published.

So the workbench is not just a command wrapper. It is the controlled path between authority documentation and derived wiki output, with publication state still anchored in the main repo instead of being inferred from the wiki repo alone.

Scope Boundary

Use the workbench when the change is mainly about:

  • governed documentation-package iteration
  • wiki-authority preparation
  • publication-prep evidence
  • bundle-refresh readiness

Do not treat it as the primary surface for:

  • Windows comparison-report proof
  • installed-extension milestone testing
  • extension runtime benchmark work

It is also not the place to invent new product truth. If a wiki page needs a claim that does not already exist in governed authority docs, the repo docs must be strengthened first.
