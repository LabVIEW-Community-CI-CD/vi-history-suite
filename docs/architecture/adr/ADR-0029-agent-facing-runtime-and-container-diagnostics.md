# ADR-0029: Agent-Facing Runtime And Container Diagnostics

- Status: Accepted
- Date: 2026-07-22

> Authoritative requirement: VHS-REQ-710 (NI LabVIEW Linux Container Setup
> Diagnostics), a child of system requirement VHS-SYS-REQ-013 (CI And Developer
> Environment). The requirements package holds the authoritative text; this ADR
> is the retained design record.

## Context

Getting a real LabVIEW comparison to run requires a specific runtime to be set up
correctly — for the container variant that means Docker, the NI LabVIEW Linux
image, and the in-container `LabVIEWCLI`, LabVIEW engine, and `lvcompare`. When
any piece is missing, an agent previously had to hand-run a scatter of ad-hoc
`docker` probes and interpret the results, which is slow, error-prone, and easy to
misread (a missing image looks like a missing CLI which looks like a licensing
problem). The project is also moving toward diagnostics across **all hardware
variants** (container, host-native, and the tangled Windows/Vagrant mirrors), so a
one-off script is not enough — a reusable, deterministic diagnostics contract is
needed.

Separately, captured runs carry a fiducial-and-stopwatch **synchronization
pattern** (four corner fiducials bounding a forty-bit machine strip of preamble,
centiseconds, and checksum). How that pattern breaks is a compact failure
signature that localizes a fault far faster than frame-by-frame inspection, but
that knowledge lived only in the (now vendored, mprr-decoupled) TDMS tooling.

## Decision

Establish a dedicated diagnostics capability, owned by vi-history-suite, built as
**pure, deterministic engines behind dependency-injected boundaries**:

- A container-diagnostics engine turns gathered probe readings into an ordered set
  of fail-closed staged checks (docker CLI, docker daemon, image presence,
  in-container LabVIEWCLI, LabVIEW engine, `lvcompare`, licensing). A check whose
  prerequisite is unmet is recorded `skip`, never a misleading `pass`; the verdict
  is worst-of with a single `readyToCompare` boolean and the next remediation. A
  `variant` label carries the hardware/runtime variant so the same contract
  generalizes into an all-variants matrix. A CLI gathers the real probes through
  an injected `docker` boundary and renders text / JSON / schema / Markdown.
- `lvmerge` is explicitly **out of scope**: changes are generated by the novel
  capture/compare procedure, not the LabVIEW merge tool.
- A synchronization-pattern analyzer decodes the fiducial-and-stopwatch sequence
  and classifies the dominant failure signature in root-cause order (missing
  fiducials, out-of-bounds strip, preamble mismatch, checksum mismatch,
  non-monotonic, stalled, or gapped centiseconds).

Rejected: extending an existing runtime ADR (the diagnostics are a distinct,
reusable capability that spans variants and the sync pattern, warranting their own
design record) and shipping the probes as ad-hoc shell (not testable, not
composable).

## Consequences

- The engines are unit-tested without a container (probes injected), so the
  readiness and failure-signature contracts are verified deterministically; the
  CLI performs the real docker probing on a capable host.
- On a maintainer host that has Docker, the NI image, and LabVIEWCLI, the
  container-readiness diagnostic can be wired as an **enforcing** pre-commit gate.
- The diagnostics leverage the vendored, mprr-decoupled TDMS infrastructure under
  `tools/tdms` and never author `.vi` binaries.
- Follow-on: additional variant diagnostics (host-native, windows-container, the
  Vagrant mirror) extend the same engine and schema additively; new staged checks
  append to the order and preserve skip-on-unmet-prerequisite staging.
