# Authoritative Deep-Research Report for `vi-history-suite` (Future-Facing Workstreams)

**Generation date (America/Los_Angeles): 2026-04-02**

## Executive Summary

`vi-history-suite` is past the point where a single pairwise VI Comparison
Report is the main product artifact. The highest-value next step is a
dashboard-centered review system that concentrates multiple retained NI
comparison reports for one VI across a commit window and helps an expert
reviewer decide where to focus first without hiding the raw evidence.

The main research conclusion is:

- The product should treat the dashboard packet, not the individual pairwise
  report, as the primary review surface for high-volume VI history review.
- Pairwise NI reports should remain the raw evidence layer and be preserved as
  drill-down artifacts.
- The dashboard should avoid semantic overreach. It can reorder, recollect,
  and surface explicit facts, but it should not claim to infer LabVIEW intent
  or correctness from images and HTML sections alone.
- Mixed-provider contribution should be modeled explicitly. A report generated
  by host-native x32 and a report generated by a future isolated Windows x64
  provider should coexist in one dashboard only if each pair entry retains
  provider, engine, bitness, artifact identity, and blocked/failure facts.
- The extension should grow a first-class runtime-doctor surface and a
  dashboard-refresh UX that makes provider choice, runtime rejection, and next
  user action understandable without reading raw logs first.

Source-backed foundation:

- VS Code webviews support secure local artifact presentation through
  `asWebviewUri`, `localResourceRoots`, and CSP discipline.
- Workspace trust and restricted configuration declarations are the right
  manifest/runtime mechanism for any extension that launches external tooling.
- VS Code extensions can run across local and remote extension hosts, and
  `extensionKind` should be chosen deliberately when the product depends on
  host-local runtime/provider behavior.
- VS Code publishing and CI guidance supports a release path with `vsce`,
  `@vscode/test-electron`, and GitLab CI artifact retention.

Empirical artifact observations:

- A real NI-generated comparison report already available in the workspace uses
  a stable HTML structure with:
  - report title
  - generation-time paragraph
  - first/second VI paths
  - overview image sections
  - included-attributes list
  - detailed information sections
- That shape is rich enough to support dashboard recollection, image
  concentration, and chronology-aware drill-down without inventing new report
  semantics.

## Dashboard Information Model And Data-Concentration Strategy

### Source-backed statements

- VS Code webviews are a valid primary review surface for local artifacts when
  the extension rewrites local file references through `asWebviewUri` and
  constrains file access with `localResourceRoots`.
- Webview CSP should start from a deny-by-default posture and re-enable only
  the local sources the review surface actually needs.
- Workspace-scoped storage through `context.storageUri` is the right place for
  large generated extension artifacts tied to one workspace.

### Empirical artifact observations

The retained NI comparison report at:

- `/home/sveld/code/standards/comparevi-system-design-benchmark/artifacts/windows-ni-vip-preinstall-v1.3.28-v0.6.12/compare-report-winhost.html`

contains:

- one report title
- one generation time
- first/second VI path display
- overview image pairs for front panel and block diagram
- one explicit included-attributes list
- one or more detailed-information sections

The adjacent asset directory contains images such as:

- `fp_1.png`
- `fp_2.png`
- `bd_1.png`
- `bd_2.png`

That observed structure supports a dashboard packet with these strata:

1. Commit-window scope
- selected VI identity
- ordered commits in scope
- retained adjacent pairs in scope
- provider coverage summary

2. Pair entry
- selected hash
- base hash
- provider
- engine
- bitness
- runtime state
- blocked/failure reason
- archived packet/report artifact paths

3. Concentrated NI report facts
- compared VI paths
- included attributes
- overview images
- detailed-information section headings and lines

4. Review cues
- newest/oldest pair markers
- missing/blocked pair markers
- provider diversity markers
- drill-down links to raw packet/report artifacts

### Recommended dashboard strategy

- Keep the dashboard chronology-first.
  - Order pair entries by commit-window chronology, newest-first by default,
    while retaining clear base/selected pairing.
- Add concentration cues that are factual, not semantic.
  - number of archived pairs
  - number of missing/blocked pairs
  - number of pairs with overview images
  - number of pairs with included-attribute changes
  - number of pairs with detailed-information sections
- Keep raw drill-down first-class.
  - dashboard entry to packet HTML
  - dashboard entry to raw NI report HTML
  - dashboard entry to archived images

## Implementation Guidance By Workstream

### 1. Multi-report developer dashboard for expert LabVIEW review

#### Source-backed statements

- Webviews are suitable for rich, extension-owned HTML review surfaces.
- Local artifact access must stay constrained through `localResourceRoots`.
- Extension-host architecture supports local and remote hosts, so dashboard
  storage and rendering must stay workspace-scoped rather than ambient-temp
  scoped.

#### Empirical artifact observations

- NI report HTML already exposes the minimum facts needed for recollection:
  image-backed overviews, included attributes, and sectioned detail blocks.

#### Recommendation

- Make the dashboard HTML the primary expert-review artifact for one VI across
  a commit window.
- Render three major regions:
  - commit-window header
  - concentrated pair grid or ordered list
  - drill-down evidence pane
- Keep pair provenance visible on every card/row.
- Surface missing/blocked reports inline, not in a separate failure-only area.

### 2. High-volume dashboard triage and prioritization cues

#### Source-backed statements

- No official source reviewed here supports automated semantic ranking of VI
  visual changes from NI HTML alone.

#### Empirical artifact observations

- NI report HTML exposes repeated structures that can be counted without
  speculation:
  - overview image presence
  - included-attribute entries
  - detailed section count
  - runtime success/failure/blocked state

#### Recommendation

- Prioritize using explicit evidence density and chronology, not semantic
  importance scores.
- Good first cues:
  - pairs with generated NI reports before pairs with only packet metadata
  - pairs with overview images before pairs without images
  - pairs with detailed-information sections before empty/blocked pairs
  - newest-first chronology, with a toggle for oldest-first
- Add a dashboard-wide coverage banner:
  - pairs in scope
  - archived pairs
  - missing pairs
  - blocked pairs
  - provider mix

### 3. Mixed-provider dashboard contribution

#### Source-backed statements

- Extension hosts can run locally or remotely, and extension location matters.
- Workspace trust should gate all external tooling paths.
- Existing NI toolchains have materially different behaviors across engines and
  host/runtime configurations.

#### Recommendation

- Normalize provider provenance into the pair entry itself:
  - `providerId`
  - `engine`
  - `bitness`
  - `executionHost`
  - `runtimeSelectionReason`
  - `blockedReason` or `failureReason`
- Do not collapse x32 host-native and x64 isolated-container evidence into one
  undifferentiated report stream.
- The dashboard should allow filtering by provider while still presenting one
  combined chronology.

### 4. Human decision-support model

#### Recommendation

- Keep three distinct artifacts:
  1. raw pairwise report evidence
  2. dashboard packet for one VI and one commit window
  3. human decision record
- Decision records should answer:
  - what VI was reviewed
  - what commit window was considered
  - what dashboard version/artifact was used
  - what bounded decision was made
  - what unresolved uncertainty remained
- The dashboard should include explicit scope language:
  - what is directly observed
  - what is absent
  - what still requires manual LabVIEW review

### 5. Runtime doctor and developer experience

#### Source-backed statements

- Workspace Trust supports manifest/runtime declarations for trust-sensitive
  behavior.
- Webviews support message passing, which is sufficient for live progress and
  doctor updates.
- VS Code status surfaces include notification progress and status bar items.

#### Recommendation

- Add a runtime doctor surface separate from the raw report panel.
- The doctor should show:
  - discovered provider/tool paths
  - selected provider and engine
  - rejected alternatives and why
  - trust blockers
  - next user action
- Progress should be dual-surface:
  - `window.withProgress` for explicit long-running tasks
  - status bar item for background continuity
  - webview progress for dashboard refresh/report-generation flows
- Cancellation should retain partial evidence instead of clearing the packet.

### 6. Packaging, release, and adoption for a dashboard-centric extension

#### Source-backed statements

- VS Code publishing guidance supports `vsce package` and tag-based publish
  flows.
- Continuous integration guidance explicitly covers `@vscode/test-electron`
  and GitLab CI with headless display setup.

#### Recommendation

- Release the extension as a dashboard-centric product, not only a history
  viewer.
- Retain these CI artifacts:
  - VSIX
  - unit/integration reports
  - harness smoke reports
  - canonical dashboard HTML/JSON artifacts when generated in CI-safe lanes
- Add a release checklist that verifies:
  - dashboard command present
  - pair archive compatible
  - smoke/report lanes produce truthful retained artifacts

## Risks, Ambiguities, And Explicit Assumptions

### Risks

- Dashboard overreach risk:
  - concentration cues may be misread as semantic judgment if language is not
    tightly factual.
- Provider-mixing risk:
  - x32 host-native and x64 isolated-provider outputs may be misread as
    equivalent unless provenance is explicit in every pair entry.
- Artifact-volume risk:
  - retaining many pairwise images and HTML reports can enlarge workspace
    storage quickly.

### Ambiguities

- Official NI docs reviewed for this round do not define a product-level
  method for concentrating multiple VI Comparison Reports into one dashboard.
- Official docs also do not define a semantic ranking scheme for many
  pairwise report transitions; any prioritization beyond explicit retained
  facts would be an implementation inference.

### Explicit assumptions

- Empirical NI HTML parsing remains acceptable as long as it is clearly labeled
  as empirical and backed by retained artifacts.
- The product continues to prioritize expert LabVIEW users reviewing
  open-source repositories with heavy VI churn.
- A future isolated Windows x64 provider will contribute evidence into the same
  dashboard packet rather than forcing a separate dashboard product.

## Acceptance Criteria For Each Workstream

### Dashboard concentration

- One selected VI with at least three commits can produce one retained
  dashboard packet.
- The dashboard shows multiple adjacent pair entries with explicit provenance.
- Missing or blocked pairs are visible inline.

### High-volume triage

- The dashboard reduces the default need to open every pairwise report.
- Triage ordering is explained by factual cues, not opaque scoring.
- Raw report drill-down remains available.

### Mixed-provider contribution

- A pair entry records provider, engine, bitness, and runtime state.
- The dashboard can show a mixed-provider commit window without hiding which
  provider produced which evidence.

### Human decision-support

- The dashboard packet and the human decision record remain separate artifacts.
- The dashboard includes explicit confidence/scope boundaries.

### Runtime doctor and DX

- A user can tell why a provider was chosen or rejected without reading raw
  logs first.
- Progress and cancellation retain partial evidence rather than failing
  silently.

### Packaging and release

- CI can produce repeatable extension test evidence.
- Release artifacts can retain dashboard/report proof surfaces, not only unit
  test output.
